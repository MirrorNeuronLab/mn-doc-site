title: "Job bundles and execution manifests"

When you start from a [blueprint](./blueprint-standard.mdx), the SDK reads the source documents, resolves configuration, and generates an executable manifest for Core. Use the source blueprint format when authoring a normal package. The execution manifest is useful when inspecting a prepared bundle or writing an explicit integration.

## Bundle structure

A submitted bundle contains a manifest and may carry a `payloads/` tree with scripts, code, images or build inputs, policies, templates, and seed files. During preparation the runtime stages the files workers need. Generated descriptors include resolved configuration. Treat prepared bundles and exports as potentially sensitive.

## Read the execution manifest

| Field | What to look for |
| --- | --- |
| `apiVersion`, `kind`, `manifest_version` | Execution format. Current generated manifests use `mn.workflow/v1` and `Workflow`. |
| `graph_id`, `job_name`, `type` | Graph identity, display name, and execution type. |
| `entrypoints`, `initial_inputs` | Starting node IDs and any initial messages. |
| `flow.nodes`, `flow.edges` | Worker nodes and message routes. A logical DAG can also carry `flow.steps` and `flow.graph.edges`. |
| `services`, `required_services` | Services the job registers or needs before starting. |
| `policies` | Restart and resource policy. |
| `metadata.job_data.resources` | Named persistent directories shared by this job's runs. |

Each worker has a `node_id`, an `agent_type`, and configuration for its runner. Inspect worker requirements and service checks when a bundle cannot start. See [Resources and devices](./resources-and-devices.mdx) and [Services and health checks](./services-and-health-checks.mdx).

## Package payloads and dependencies

Keep runtime asset paths relative to `payloads/`. OpenShell uploads map an explicitly declared source file into the sandbox. HostLocal nodes can declare `python_environment.requirements` and `python_environment.packages` to build a cached Python environment. A root-level `requirements.txt` is for development unless your runtime configuration explicitly stages and references it.

For authored blueprints, declare skill, agent, and SDK component dependencies in `dependencies.json`. Prepared bundles may carry source trees or wheels. Payload package names and versions must match their distribution metadata. Review code and installation hooks before using a package from another author.

Blueprint-owned model files can be declared as `type: "payload"` sources. Keep GGUF, Safetensors, or DDUF files and their licenses under `payloads/`. Preparation validates paths and streams large assets into runtime storage. See [Configure and diagnose models](./model-runtime.mdx).

## Persistent data and outputs

Declare persistent resources in the blueprint's storage configuration. Each job owns its data across runs. Seed directories are applied when that data is initialized or explicitly reset. Use run-scoped artifacts for individual outputs. For isolated runners, declare output handoff and any configured-folder export explicitly. See [File inputs and output handoff](./docker_and_openshell_for_blueprints.mdx#file-inputs-and-output-handoff).

## Load and run a reviewed bundle

For a source blueprint, start with `mn blueprint validate ./my-blueprint`. To create a durable job from a reviewed local bundle, attach to a local runtime and work from the bundle's parent directory.

```bash
mn job create ./bundle --job-id document-review
mn job show document-review
mn job start document-review
```

Review its configuration and external effects before the last command. Keep the public run ID from the start receipt and [monitor the run](./monitor.mdx). For an application that uploads a ZIP, use [Upload a package and create a job](./api.mdx#upload-a-package-and-create-a-job).
