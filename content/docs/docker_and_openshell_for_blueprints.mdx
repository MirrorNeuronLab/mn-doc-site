title: "Prepare files and services for Docker and OpenShell"
description: "Stage inputs, publish outputs, and configure service access across runner boundaries."
---

Check which environment needs each file or endpoint. The application surface reads its own filesystem. The runtime prepares bundles on the owner machine. A Docker worker sees its image, mounts, and container network. OpenShell sees the files and network access allowed by its sandbox policy.

## File inputs and output handoff

Keep static scripts, templates, and policies under `payloads/`. Declare user files or folders for staging and use a path the preparing runtime can read. Use a supported upload when the source file is on the client. In a remote catalog launch, paths are resolved on the runtime.

Use `local_inputs.folders` to map an operator's configured folder to a staged path. The example limits staging to PDF and text files.

```json
{
  "documents": {"folder_path": ""},
  "local_inputs": {
    "folders": [
      {
        "config_path": "documents.folder_path",
        "payload_path": "worker/mn_local_inputs/documents",
        "runtime_path": "mn_local_inputs/documents",
        "allowed_extensions": [".pdf", ".txt"]
      }
    ]
  }
}
```

The worker must receive the `worker/` payload tree and start from the corresponding working directory. Each worker needs its own accessible staged path. Validation can run during preparation and again against the staged bundle. A command validator reading `MN_BLUEPRINT_CONFIG_JSON` must handle the path it receives at each stage.

For OpenShell, declare uploads and the sandbox working directory. Use `artifact_handoff.version: "mn.artifact_handoff/v1"` and declare output files. To copy them to a configured folder, also set `artifact_handoff.export_outputs: true`. The runtime verifies the handoff before publishing outputs. See [Artifact handoff](./runtime-architecture.mdx#why-artifacts-matter).

## Ports and network access

A loopback address refers to the environment that makes the connection. Check model endpoints, callbacks, and health probes from the worker or check environment. OpenShell policies must allow the hostnames and routes the workflow uses. Review those routes before passing credentials.

A reserved port helps the scheduler avoid conflicts. Configure Docker or the runner to publish the intended listener. An already published port may appear occupied on the host because Docker owns it. Use the reachable address and port in the readiness check.

For a job UI, declare a long-running service, its port, and a passing check. Use the job's [UI relay](./api.mdx#job-ui-relay) for browser access to the allowed service ports.

## Diagnose a runner or service

1. Run `mn blueprint doctor ./my-blueprint` from the parent of the reviewed package.
2. Confirm the owner and runner, then check the staged paths, mounts, and working directory.
3. Inspect `mn service show <service-name> --all` for unhealthy instances.
4. Follow [run events and logs](./monitor.mdx#logs-events-and-results) to see whether preparation, launch, or output transfer failed.

See [Execution and data access](./security.mdx) before changing mounts, network access, or sandbox policy.
