---
title: "Configure Redis failover"
description: "Connect one runtime to a Redis Sentinel group and verify its elected primary."
---

Core stores job state, leases, and other coordination data in Redis. A default `single` configuration connects through `MN_REDIS_URL`. Use `sentinel` when the owning runtime should discover a primary from a Redis Sentinel group. Each federated Core needs a distinct writable store identity. Plan Redis failover separately for each owner.

## Runtime configuration

Configure these values in the owning Core's deployment environment before starting it. Keep a copy of the previous settings for rollback.

| Setting | Value or purpose |
| --- | --- |
| `MN_REDIS_HA_MODE` | `sentinel` |
| `MN_REDIS_SENTINELS` | Comma-separated reachable Sentinel endpoints such as `redis-a.example:26379,redis-b.example:26379` |
| `MN_REDIS_SENTINEL_MASTER` | The monitored master name. Default `mirror-neuron`. |
| `MN_REDIS_SENTINEL_PORT` | Default Sentinel port for endpoints without a port. Default `26379`. |
| `MN_REDIS_DB` | Redis database index. Default `0`. |
| `MN_REDIS_URL` | Connection scheme in Sentinel mode. |
| `MN_REDIS_USERNAME` and `MN_REDIS_PASSWORD` | Credentials for Redis. |
| `MN_REDIS_SENTINEL_USERNAME` and `MN_REDIS_SENTINEL_PASSWORD` | Credentials for Sentinel when required. |

Use endpoints reachable from Core's network. If a Sentinel returns an internal hostname that Core cannot resolve, correct the announced address or configure `MN_REDIS_SENTINEL_HOST_MAP` for deliberate hostname translation.

## Join a managed Redis group

If you use the Core checkout's `scripts/redis_ha.sh` helper, run it from `MirrorNeuron`. Use dedicated hosts or ports and a trusted network. The helper publishes Redis and Sentinel listeners and requires a Redis password. Set it securely in `MN_REDIS_PASSWORD` before running the command. Set a separate Sentinel password if your configuration needs one.

```bash
bash scripts/redis_ha.sh join \
  --self-host <this-host> \
  --sentinels <sentinel-host-list> \
  --master-name mirror-neuron \
  --quorum <quorum>
```

Use each host's reachable address for `<this-host>` and a comma-separated list of Sentinel host and port pairs. Choose quorum for the number and placement of your voters. Production Sentinel groups use at least three voters. Follow the managed group procedure when Redis is operated by another service.

## Verify and troubleshoot

Use the configured Sentinel credentials from a trusted host. Substitute your Sentinel host and monitored master name.

```bash
redis-cli -h "<sentinel-host>" -p 26379 SENTINEL get-master-addr-by-name mirror-neuron
```

Verify that the returned address is reachable from Core. Restart the owning runtime in its maintenance window and check `mn runtime status` and `mn runtime doctor` on a combined install, or `bin/mn-runtime status` and `bin/mn-runtime doctor` on a dedicated runtime.

During promotion, Core retries reconnectable Redis errors such as `READONLY`. If errors persist, check Sentinel leadership, replica health, and advertised addresses. `MN_REDIS_WAIT_REPLICAS` can request replica acknowledgements on selected durable writes. A wait timeout can follow a committed primary write, so read the current record before retrying.

## Remove a member

Use `bash scripts/redis_ha.sh leave --help` to review the helper options and confirm that another primary or failover candidate is available. The leave operation can promote another primary before detaching the local instance. It preserves data by default. `--purge-local` flushes the detached local database, so back up needed data before using it.

For peer membership, use [Connect runtime nodes](./cluster.mdx).
