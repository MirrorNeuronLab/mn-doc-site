---
title: "Federation behavior"
description: "Understand what your runtime shares with peers and where to find authoritative job state."
---

Connect peers through a trusted network using [Connect runtime nodes](./cluster.mdx). A surface can reach multiple peers through one entry runtime. When you start a job, one selected runtime owns the job, its runs, and its durable execution state.

## Read remote state

An entry node forwards a request to the job's owner. A cached summary can still appear when that owner is unreachable. Check its availability and last sync time before using it to make an operational decision. Streams, logs, and artifacts require access to the owner.

## Plan for an unavailable owner

A partition can leave work running on the owner. Recovery stays with that owner and its writable Redis store. File synchronization can copy bundles and outputs between peers while the owner's Redis retains execution authority.

Use [Moving an idle job](./cluster.mdx#moving-an-idle-job) to transfer a quiescent job intentionally. See [Redis failover](./redis-ha.mdx) to give one owner's store a failover path.
