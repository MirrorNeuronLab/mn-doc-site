---
title: "Reliability and recovery"
description: "Know what happens during pauses, retries, cleanup, and owner outages."
---

A job's owning runtime keeps the authoritative execution state. Observe work by its public run ID. After an interrupted command, read the run or operation receipt before submitting again. Accepted work can continue after a client disconnects.

## Pause and resume

Pause stops admission of new work in the run and interrupts active attempts as the runner allows. Resume uses the durable state and remaining budgets. A paused run can retain its resource reservation and model residency. If you need to release capacity, cancel the run and wait for cleanup.

## Cancellation and cleanup

Cancellation records intent and fences the old execution attempt before cleaning up its processes, containers, services, and model leases. Use `mn run show <run-id>` and owner diagnostics to verify progress. The runtime can report terminal state while resource cleanup is still pending. An offline node can acknowledge its part of cleanup after it rejoins.

Run deletion removes execution records and artifacts. Job data has a separate lifecycle. Back up needed evidence before deleting a run, resetting job data, or replacing a service run. Cancelled workers' external effects still need to be handled in the external system.

## Manual checkpoint retry

For a failed run, inspect the retained checkpoint to see whether it is eligible for retry.

```bash
mn run retry <run-id> --dry-run
```

Check which steps are preserved or retried and resolve blockers first. A retry keeps the run ID and starts a new attempt. It can reuse verified completed steps and retained inputs. Missing artifacts, incompatible saved data, or uncertain effects can block retry.

```bash
mn run retry <run-id> --queue
```

Use `--queue` when you want the retry to wait for capacity. Supply `--set PATH=VALUE` only for settings the blueprint declares adjustable on retry. Save the printed idempotency key, expected attempt, and checkpoint revision. If you lose the response, inspect the existing run first. To resubmit the same retry, pass all three options, `--idempotency-key`, `--expected-attempt`, and `--checkpoint-revision`, with the same settings.

## Restart and replay

The owner can recover from durable state according to the run's restart policy and the safety of replaying its work. A restarted worker reads persisted records and retained inputs. It rebuilds in-memory state as it runs. Use stable idempotency keys for externally visible actions so repeated deliveries can be reconciled. When the runtime reports `paused_for_review`, check the evidence and address any uncertain effects before continuing.

## Partition and restart behavior

A federated peer can show stale summaries while an owner is unreachable. Current controls and outputs require reaching the owner. Some offline job archive or confirmed deletion requests can appear as `archive_pending` or `delete_pending`. Check the owner after reconnection for the final result. Use [Redis failover](./redis-ha.mdx) to protect the owner's coordination path and [Moving an idle job](./cluster.mdx#moving-an-idle-job) for a deliberate transfer.
