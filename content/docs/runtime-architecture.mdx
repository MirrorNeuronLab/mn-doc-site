## Application surface and runtime nodes

The CLI and API surface connects to a runtime over authenticated gRPC. The entry runtime accepts requests and forwards them when a peer owns the job. The owner prepares the package, checks capacity, and uses its Redis state to coordinate the run. Workers run through the declared HostLocal, Docker, or OpenShell runner.

```text
CLI or Web UI → entry runtime → job owner → runner → worker
                                      ↓
                             Redis state and run files
```

The Web UI reaches the runtime through the API. For placement, health checks, and scheduling, see [Runtime orchestration features](./nomad-inspired-runtime.mdx). A CLI or API process can disconnect while the owner continues preparing or executing work. Reattach using the returned operation or run ID. See [Install MirrorNeuron](./installation.mdx) and [Connect runtime nodes](./cluster.mdx).

## Admission and supervision

The owner reserves capacity before executing workers. Queued starts have durable IDs and wait for an eligible reservation. Once running, workflow dependencies and the step ledger determine when a worker may handle a delivery and when its output is committed.

Preparation of models, dependencies, and services has separate deadlines from execution. Core can inspect a step when it reaches its inactivity interval. Useful progress or a bounded external wait can justify continuing the same attempt. Explicit operation and runner timeouts still apply. When a run is quiet, check events, preparation status, and human requests before assuming it has failed.

## Workflow action allowances

Use `execution.json` `policies.workflow_budgets` to cap named workflow actions. Compilation resolves declared configuration values into bounded integer limits. The owner records grants and restores the allowance on a verified checkpoint retry. An uncertain action can still count against the limit.

Use [Run resource budgets](./resources-and-devices.mdx#run-resource-budgets) for CPU, memory, disk, and GPU capacity. Use [Reliability and recovery](./reliability.mdx) for replay and idempotency.

## Why artifacts matter

Publish large files as artifacts and send their references through workflow messages. Keep the run ID, output path, and required source evidence together so another step or application can verify the result.

An OpenShell handoff validates its producer and the declared paths, sizes, and hashes before committing outputs. If transfer fails after a known command completion, retry can reuse that outcome. An uncertain dispatch can require review. For shared storage, wait for the verified output or completion inventory before copying results from another machine.

Use [Monitor and control runs](./monitor.mdx#logs-events-and-results) to download available results and [Docker and OpenShell](./docker_and_openshell_for_blueprints.mdx#file-inputs-and-output-handoff) to declare staged inputs and outputs.
