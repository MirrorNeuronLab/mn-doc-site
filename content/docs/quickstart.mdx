title: "Run your first blueprint"
description: "Check a local blueprint, start a run, and download the outputs."
---

## Before you begin

Complete a combined [installation](./installation.mdx) or attach your client to a runtime on the same machine. Obtain a blueprint folder and read its README, configuration, dependencies, and worker files. Use the blueprint's sample inputs for this first run. Run the commands from the folder that contains the blueprint and replace `./my-blueprint` with its path.

A blueprint can execute code, read files, and call external services. Review those actions and any credentials the blueprint can use before starting it. See [Execution and data access](./security.mdx).

## 1. Check your connection

```bash
mn node list
```

Check that your local runtime appears. On a combined installation, run `mn runtime status` to verify service health. If you installed with `--no-start`, use `mn runtime start` first.

## 2. Check the blueprint

```bash
mn blueprint validate ./my-blueprint
mn blueprint doctor ./my-blueprint --check-only
```

Validation checks the package and its declared requirements. Doctor in check-only mode inspects declared dependencies. For deeper runtime probes, run it without `--check-only` after reviewing the blueprint's model and service access. Resolve errors about inputs, services, hardware, or [models](./model-runtime.mdx) before proceeding. For a remote runtime, choose a [catalog blueprint](./examples.mdx) with inputs accessible on that runtime.

## 3. Start the run

```bash
mn blueprint run ./my-blueprint --detached
```

Save the returned job ID and run ID. `--detached` starts the work without opening the live workflow view. If capacity blocks the start, check whether the runtime created a job. To queue a saved job, use `mn job start <job-id> --queue`. If you still need to create the job, add `--queue` to the blueprint launch. An accepted queued request already has a run ID, so track that run while it waits. See [Admission and queueing](./resources-and-devices.mdx#admission-and-queueing).

## 4. Follow the run and retrieve the result

Open the run with the public ID returned at launch.

```bash
mn run show <run-id>
mn run watch <run-id>
```

Ctrl+C closes the watcher. The run continues on its owner. Wait for a terminal state before downloading outputs. Use the logs to check what the workflow did.

```bash
mn run logs <run-id> --channel logs
mn run result <run-id>
```

Look for the downloaded files under `$MN_HOME/outputs/<run-id>` on the machine that ran the command. Review warnings and check the outputs against the blueprint's expected result before using them.

## Clean up

Use `mn run cancel <run-id>` to stop unfinished work and retain its history. External actions that already happened still need to be handled in the external service. If you started the local runtime for this tutorial, stop it with `mn runtime stop` when it is idle.

To view events, respond to a request, or troubleshoot a failed run, see [Monitor and control runs](./monitor.mdx).
