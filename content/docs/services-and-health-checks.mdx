---
title: "Services and health checks"
description: "Declare a service, verify readiness, and find passing instances."
---

A blueprint can declare services it provides and services it needs before starting. The runtime registers services and uses health checks to decide which instances are ready.

## Find a service

Use the attached CLI to list services and inspect an instance.

```bash
mn service list
mn service show <service-name>
mn service list --all
```

Discovery normally returns passing instances. Add `--all` to include unhealthy instances when troubleshooting. Use `--node <node>` to inspect a specific runtime or `--tag <tag>` with `service show` to filter a name.

## Declare a service and its dependencies

Add service declarations in the blueprint's execution role. Use job-level `services` for services provided by the job and `required_services` for prerequisites. Agent-level `services` registers an instance with the worker. Use agent-level `requires_services` when the selected node must have a matching service.

Use the host and port reachable from the check environment. This service example expects an HTTP response with status 200.

```json
{
  "name": "worker-api",
  "address": "127.0.0.1",
  "port": 61000,
  "tags": ["blueprint"],
  "checks": [
    {
      "name": "ready",
      "type": "http",
      "path": "/healthz",
      "expected_status": 200,
      "timeout_ms": 2000,
      "interval_ms": 10000,
      "required": true
    }
  ]
}
```

HTTP checks can verify status and response text. TCP checks test reachability. A gRPC check can query service health. Script checks execute an argument vector, so review the command and where it runs. Set check timeouts and intervals for the service you operate.

## Verify readiness before launching

From the parent of a reviewed local blueprint, use `mn blueprint doctor ./my-blueprint`. If a required service fails, check its instance health and test the address from the environment running the check. A published host port and a container's internal port may differ. See [Docker and OpenShell network boundaries](./docker_and_openshell_for_blueprints.mdx#ports-and-network-access).

## Publish a job's own Web UI

Declare the UI worker, its listening port, its service name and tags, and a readiness check. The runtime supervises the declared process and publishes a healthy service through discovery. Use `GET /api/v1/jobs/{job_id}/ui` to find the current descriptor. The relay checks the current execution and allowed ports before forwarding. See [Job UI relay](./api.mdx#job-ui-relay) for the client interface.
