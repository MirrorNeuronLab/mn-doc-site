## Output and automation

Add `--json` to a command for structured output. One-shot responses use schema `mn.cli/v1` with `ok`, `data` or `error`, `warnings`, and `meta`. Followed commands use newline-delimited `mn.cli.stream/v1` records. Progress and diagnostics go to stderr. Set `MN_CLI_OUTPUT=plain` for plain text or `NO_COLOR=1` to remove color. Use `mn --debug` before the group to show additional sanitized diagnostics.

| Exit code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | Operational or critical diagnostic failure |
| `2` | Usage, validation, missing resource, or confirmation failure |
| `13` | Authorization failure |
| `130` | Interrupted command |

Where offered, `--dry-run` previews the action and `--yes` confirms it. In non-interactive or JSON mode, destructive operations need `--yes` or `--dry-run`. Check help for what a command's `--force` overrides.

## Blueprints

| Task | Command |
| --- | --- |
| Browse the CLI's configured catalog | `mn blueprint list` |
| Read a blueprint's details | `mn blueprint show <blueprint-id>` |
| Prepare a catalog blueprint | `mn blueprint add <blueprint-id>` |
| Refresh the catalog | `mn blueprint update --all` |
| Check a local folder | `mn blueprint validate ./my-blueprint` |
| Diagnose a local folder without preparing environments | `mn blueprint doctor ./my-blueprint --check-only` |
| Start a catalog blueprint | `mn blueprint run <blueprint-id> --detached` |
| Export a run report | `mn blueprint export <run-id> --format markdown --output report.md` |

Use an explicit path for a local package and attach to a runtime on the same machine. Catalog launches resolve the ID and input paths on the connected runtime. `--set PATH=VALUE` overrides declared settings at launch. To preview blueprint removal, use `mn blueprint remove <blueprint-id> --dry-run`. Review owned data and models before confirming. See [Choose a blueprint](./examples.mdx).

## Jobs and runs

Run the create example from the parent of a reviewed local bundle. Then use its job ID and the run ID returned by `job start`.

```bash
mn job create ./bundle --job-id daily-review
mn job show daily-review
mn job start daily-review
mn run list --job daily-review
mn run show <run-id>
mn run watch <run-id>
mn run result <run-id>
```

Use `mn job start <job-id> --inputs ./inputs.json` to pass workflow inputs from a JSON file. Use `--queue` on `job start` or `blueprint run` to accept a wait for capacity. Save the returned run ID. See [Inspect or defer a queued run](./schedules-and-events.mdx#inspect-or-defer-a-queued-run).

For a failed run, preview `mn run retry <run-id> --dry-run`. Retry keeps the run ID and advances the attempt. Use `--queue` to accept a wait and `--set PATH=VALUE` only for settings declared adjustable on retry. See [Manual checkpoint retry](./reliability.mdx#manual-checkpoint-retry).

> Replacing a service run permanently removes the old run's history and artifacts. Download the evidence you need before replacing it.

A service job allows one attached run. To replace it, use `mn job start <job-id> --run-id <new-run-id> --force --yes`. Job configuration and persistent data are retained. For pause, resume, cancellation, or deletion of one execution, see [Monitor and control runs](./monitor.mdx).

## Back up, restore, or move a job

Pause active runs before backup. The default air-gapped archive can include Docker images, wheels, and model files. Protect the ZIP as you would the original job data.

```bash
mn job backup <job-id> --output ./job-backup.zip
mn job restore --input ./job-backup.zip --job-id <new-job-id>
```

Restoring creates a separate job and preserves the archived execution history as evidence. Add `--start` only when you want a fresh execution after restore. For a connected destination and an idle job, see [Moving an idle job](./cluster.mdx#moving-an-idle-job). Preview data reset or job deletion with `--dry-run`. Those operations can permanently remove data.

## Models

| Task | Command |
| --- | --- |
| Browse the model inventory | `mn model list` or `mn model list --available` |
| Read registered model facts | `mn model show <model-id>` |
| Install a model on a specific node | `mn model add <model-id> --node <node>` |
| Prepare a configured default | `mn model add --default` |
| Diagnose the live model route | `mn model doctor <model-id>` |
| Verify a capability | `mn model probe <model-id> --capabilities image,json-schema,stream` |

See [Configure and diagnose models](./model-runtime.mdx) for provider files, placement, and removal.

## Runtime, nodes, and resources

| Task | Command |
| --- | --- |
| Manage the installed local runtime | `mn runtime start`, `mn runtime stop` |
| Inspect local services or the saved client connection | `mn runtime status` |
| Diagnose a combined install | `mn runtime doctor` |
| Check for an upgrade | `mn runtime upgrade --check-only` |
| Preview cleanup of unused runtime resources | `mn runtime cleanup --dry-run` |
| Connect to a runtime | `mn node add <host> --token <runtime-control-token>` |
| View membership and node health | `mn node list`, `mn node show <node>` |
| View capacity and observed usage | `mn resource show`, `mn resource usage` |
| Find available services | `mn service list`, `mn service show <service-name>` |
| Reattach to background preparation | `mn operation show <operation-id>`, `mn operation watch <operation-id>` |

Use `bin/mn-runtime` in a dedicated runtime installation for lifecycle commands. See [Connect runtime nodes](./cluster.mdx) for credentials, drain, and removal.
