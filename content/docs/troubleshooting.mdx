title: "Troubleshooting"
description: "Find the next check when a runtime, blueprint, or run fails."
---

Save the exact error, time, job ID, and run ID before changing state. Keep tokens, provider credentials, and private input paths out of shared diagnostics.

## A client cannot connect

Run `mn --version` and `mn runtime status` in the intended installation environment. In client mode, status describes the saved connection. For `MN_CLIENT_NOT_CONNECTED`, check the selected `MN_HOME`, the reachable Core host and port, and the runtime control token. Reattach with [the client connection procedure](./installation.mdx#connect-a-client-without-docker). A failed attachment keeps the previous profile.

## Runtime does not become ready

Run `mn runtime doctor` on a combined installation or `bin/mn-runtime doctor` from the dedicated runtime home. Check that Docker is running and that the required components start. For a port conflict, compare the reported listener with the intended configuration. For Redis errors, check the owning Core's Redis endpoint and service logs. If Sentinel is configured, see [Redis failover diagnostics](./redis-ha.mdx#verify-and-troubleshoot). Preserve Redis data before any cleanup.

## A local folder is treated as a catalog ID

Pass an explicit path such as `./my-blueprint`, `../my-blueprint`, or an absolute path. Local packages require an attached runtime on the same machine. On a remote runtime, launch with an ID available to that runtime and use input paths accessible there. The surface's catalog can differ from the runtime's catalog.

## A blueprint fails validation or preparation

Run the package checks from its parent directory.

```bash
mn blueprint validate ./my-blueprint
mn blueprint doctor ./my-blueprint --check-only
```

Fix the first blocking issue. For model or service errors, check the expected owner with `mn node show <node>` and use [model diagnostics](./model-runtime.mdx) or [service checks](./services-and-health-checks.mdx). For an inaccessible file, check the staging path and runner in [Docker and OpenShell](./docker_and_openshell_for_blueprints.mdx).

If your connection dropped after preparation started, use `mn operation show <operation-id>` or `mn operation watch <operation-id>` with the receipt you have. Check whether the original job or run exists before submitting again.

## A run is queued, quiet, or failed

```bash
mn run show <run-id>
mn run logs <run-id> --channel events
mn run logs <run-id> --channel logs
mn run human list <run-id> --pending
```

- For `queued`, inspect the capacity blocker and the owner. See [Inspect or defer a queued run](./schedules-and-events.mdx#inspect-or-defer-a-queued-run).
- For a pending human request, review it and respond as described in [Monitor and control runs](./monitor.mdx#human-collaboration).
- For an eligible failed run with a saved checkpoint, preview recovery with `mn run retry <run-id> --dry-run`. See [Manual checkpoint retry](./reliability.mdx#manual-checkpoint-retry).
- If work is terminal while capacity remains reserved, check for pending cleanup on the owner.

## A peer or HTTP request fails

| Symptom | Check |
| --- | --- |
| `MN_NODE_UNAVAILABLE` | Check the owner's advertised address and health. Reconnect to the owner for current data. |
| HTTP `401` | Use the surface API bearer token. Keep the runtime control token for Core attachment. |
| HTTP `412` or `428` | Read the current resource and send its ETag in `If-Match`. |
| Interrupted event stream | Reconnect with the last applied event ID, then refresh the run or operation snapshot. |

See [Connect runtime nodes](./cluster.mdx) and [HTTP API](./api.mdx) for connection and request details.
