## Package layout

A blueprint can be a directory or a ZIP with the same package structure. Put `manifest.json` at its root. Reference workflow, execution, contracts, and default configuration documents by package-relative POSIX path. Add dependencies, extensions, and payloads as your workflow needs them.

```json
{
  "$schema": "https://mirrorneuron.io/schemas/blueprint/v1/manifest.schema.json",
  "id": "document_review",
  "name": "Document review",
  "tagline": "Turn a folder of documents into a review packet",
  "description": "Collect source evidence and publish a review packet.",
  "version": "1.0.0",
  "workflow": "workflow.json",
  "execution": "execution.json",
  "contracts": "contracts.json",
  "config": "config/default.json"
}
```

| Document | Put this here |
| --- | --- |
| `manifest.json` | Blueprint identity, version, description, and references |
| `workflow.json` | Logical steps, dependencies, and workflow behavior |
| `execution.json` | Execution mode, workers, runners, resources, and service declarations |
| `contracts.json` | Inputs, validation, outputs, artifacts, and other observable contracts |
| `config/default.json` | Settings operators can tune |
| `dependencies.json` | Versioned SDK components, skills, and agents |
| `extensions/` and `payloads/` | Declared features and packaged code or assets |

Use the packaged schemas for each document. The optional `tagline` must be a single line of 1–80 characters with no leading or trailing whitespace. The catalog can display it in lists while retaining the full description on the detail page.

## Execution modes

- **Compiled.** Set `execution.mode` to `compiled`. Define the logical steps in `workflow.json` and let the SDK generate the physical agent graph. See [Use workers and skills](./blueprints-and-skills.mdx).
- **Explicit.** Set the mode to `explicit` to declare execution agents and bindings directly.

Use unique step IDs and acyclic dependencies. Define dependencies with step `needs` or a workflow `edges` list. Set `execution.type` for batch or service behavior. Put a shared worker default under `execution.defaults.worker`.

Put physical capacity settings in `execution.json` under `policies.resource_allocation`. See [Run resource budgets](./resources-and-devices.mdx#run-resource-budgets). Use `policies.workflow_budgets` for named workflow action limits. See [Execution behavior](./runtime-architecture.mdx#workflow-action-allowances).

## Dependency versions

Declare each SDK distribution in `packages` with `type: "pip"`, `source: "gar"`, its distribution name, and a version constraint. Declare reusable skills and agents under `skills` and `agents`.

Use an exact version to reproduce a released package. Supported constraints include PEP 440 ranges, compatible releases, and trailing wildcards such as `1.4.*`. Use `MN_USE_LOCAL_SKILLS=1` for source development with matching local distributions. Released preparation uses the authored constraints. A skill that declares `"setup": "on_install"` can execute a setup hook during preparation.

## Extensions

Register extension documents under `extensions` in `manifest.json`. Each entry names its `file` and whether it is `required`. Give each extension document its own schema ID.

| Registration | Use it for |
| --- | --- |
| `mn.llm` | Model profiles and worker model assignments |
| `mn.rag`, `mn.context` | Retrieval and working context |
| `mn.response`, `mn.mcp` | Job response services and declared MCP tools |
| `mn.blocks` | Reusable workflow blocks |
| `mn.storage`, `mn.airgap` | Job data and offline dependencies |
| `mn.ui`, `mn.product`, `mn.testing` | Launch presentation, discovery, and tests |
| `mn.agentic`, `mn.domain` | Bounded agent behavior and domain descriptors |

An unsupported required extension blocks compilation. An unknown optional descriptor can travel with the package as metadata.

## Loading and configuration

The SDK applies feature defaults, the referenced default configuration, `config/overwrite.json` if present, and invocation overrides in that order. Use `mn blueprint run ./my-blueprint --set PATH=VALUE` for a launch override. Keep credentials in the runtime environment or configured secret source.

The SDK reads, resolves, compiles, and prepares a package before submission. Workers receive a generated descriptor. See [Use the Python SDK](./sdk.mdx#load-and-compile-a-blueprint) to inspect the compiled fingerprint.

## Catalogs

Put published package paths in the catalog's ordered `index.json`. Use a unique blueprint ID for each entry. Git catalogs can contain folders or submodules pinned to the catalog revision. A local catalog reads the working folders directly. See [Catalog configuration](./env_variables.mdx#blueprint-catalog-resolution).

## Paths, transport, and export

Keep referenced files inside the package. Use regular files with portable relative paths. Package validation rejects path traversal, symlinks, conflicting destinations, and malformed role documents. Export a portable package outside the source folder with `export_blueprint` from `mn_sdk.blueprints`. Declare any dependency the recipient will need to fetch.

## Validate and try the package

Connect to a local runtime and validate the blueprint from its parent directory.

```bash
mn blueprint validate ./my-blueprint
mn blueprint doctor ./my-blueprint --check-only
```

Review the runner and executable payloads before preparing the package or running it. Fix blocking validation errors and try [a first run](./quickstart.mdx) with sample inputs. If a submission response is lost, inspect its job or operation before submitting again.
