---
title: "Connect runtime nodes"
description: "Join runtimes over a trusted network, verify ownership, and manage maintenance."
---

A CLI or API surface connects to an entry runtime. That runtime can federate with peers. Each peer has its own writable Redis store and can own jobs. One job's workers and execution state stay on its owner.

## Network requirements

Allow Core gRPC traffic between trusted clients and peers. The default published port is `55051`. If you use peer model gateway routing, restrict the gateway's port, normally `4000`, to the trusted network. Configure optional shared file transport separately. Keep Redis and internal distribution listeners private.

The published Core endpoint defaults to loopback. Set an appropriate `MN_GRPC_BIND_HOST` and advertise a LAN or VPN address peers can reach. Check the firewall before widening the bind. Run the start command from the installation home.

```bash
bin/mn-runtime start --host <node-address>
```

Replace `<node-address>` with that machine's reachable address. On a combined installation you can use `mn runtime start --host <node-address>`.

## Start and join two nodes

[Install and start](./installation.mdx) a combined or dedicated runtime on each machine. Obtain each runtime's reachable host and private control token from its operator. In the surface shell, set `ENTRY_HOST`, `PEER_HOST`, `ENTRY_TOKEN`, and `PEER_TOKEN` privately.

```bash
mn node add "$ENTRY_HOST" --token "$ENTRY_TOKEN"
mn node add "$PEER_HOST" --token "$PEER_TOKEN"
mn node list
```

If your combined install already uses the intended entry node, begin with the peer command. Add `--grpc-port` for a non-default port. The entry runtime checks for a distinct coordination-store identity and waits for reciprocal readiness.

## Verify federation

Use `mn node show <peer-node>` with the exact name from `mn node list`. Check that the peer is online, marked federated, and eligible to own jobs. Use `mn resource show` for capacity on each node. For local service diagnostics, check `bin/mn-runtime status` from each runtime home.

## Job ownership and routing

Use `mn blueprint run <blueprint-id> --node <node>` to choose a specific owner. If you omit the node, placement selects an eligible owner based on requirements and available models. The entry runtime forwards operations to that owner. Its cached remote summaries can show `owner_available`, `projection_stale`, and `last_synced_at`.

If connectivity breaks, existing jobs can continue on their owner. Reach that owner directly for current state if possible. Cross-peer controls, streams, and files can return `503 MN_NODE_UNAVAILABLE`. The runtime can retain certain owner-directed job archive or delete requests as pending. Verify the owner's acknowledgement before treating cleanup as complete. See [Federation behavior](./cluster_architecture.mdx) and [Partition and restart behavior](./reliability.mdx#partition-and-restart-behavior).

Managed inference for an admitted run uses its owner's reserved capacity. Hosted provider traffic follows the configured gateway route. See [Model residency](./model-runtime.mdx#run-admission-and-model-residency).

## Shared blobs are optional

Syncthing can replicate submissions and output files. Each owner continues to use its own Redis, scheduler, and leases. Derived environments and checkpoints stay local. Use `MN_SYNCTHING_REQUIRED=1` if your setup should fail startup or join when the storage sidecar cannot be prepared.

## Drain a node for maintenance

```bash
mn node drain <node> --reason "host maintenance" --wait
mn node show <node>
```

Check the drain and outstanding work before stopping the runtime or removing membership. When the host is ready, use `mn node undrain <node> --reason "host ready" --mark-eligible`. Removing a node with `mn node remove <node> --yes` changes membership and leaves its installed services and files on that machine. Removing the entry node also clears the surface's saved connection.

## Moving an idle job

Wait for terminal runs and resource cleanup, pause its schedules, and check that its data is portable. Keep a backup. The destination must be reachable and compatible.

```bash
mn job relocate <job-id> --node <destination-node>
mn job show <job-id>
```

Verify the new owner and transfer status before starting work. A move copies the job and retained evidence without replaying prior runs. If the move is interrupted, retry the same transfer. Before ownership commits, `mn job relocate <job-id> --node <destination-node> --abort` can restore availability at the source. After commit, retry the move to finish activation and cleanup.

## Troubleshoot a join

- For `MN_NODE_UNAVAILABLE`, check each runtime's advertised address, listener, and service health. Repeat the same join after fixing reachability.
- For a store identity conflict, check each Core's writable Redis configuration. Give the joining Core a distinct store before retrying.
- For stale summaries, check whether the job's owner is reachable. See [Troubleshooting](./troubleshooting.mdx).
