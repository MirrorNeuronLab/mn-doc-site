---
title: "Schedules and events"
description: "Set up recurring or delayed work and manage runs waiting for capacity."
---

A schedule belongs to a durable job and runs on its owner. A batch occurrence starts a new run. A service occurrence manages the job's single attached run.

## Create a periodic schedule

Send `POST /api/v1/jobs/{job_id}/schedules` with the API bearer credential and an `Idempotency-Key`. This request body creates a 2 a.m. daily schedule in New York time.

```json
{
  "schedule": {
    "kind": "periodic",
    "crons": ["0 2 * * *"],
    "timezone": "America/New_York",
    "prohibit_overlap": true,
    "missed_policy": "skip"
  }
}
```

Use five-field cron expressions or a supported shortcut such as `@daily`. The timezone defaults to UTC. Save the returned schedule ID and inspect the next scheduled time. See [HTTP API conventions](./api.mdx#pagination-and-safe-updates).

## Schedule a delayed launch

Attach to a local runtime and schedule the reviewed blueprint from its parent directory.

```bash
mn blueprint run ./my-blueprint --schedule 30m
```

This prepares a job and records a future start. Keep the job and schedule IDs. `--schedule` also accepts an ISO 8601 timestamp or schedule JSON. Use `--auto-schedule` on its own to create a resource-wait schedule. For an immediate attempt that can wait under the same run ID, use `--queue` on its own.

## Inspect and update schedules

Use the exact Core node name to list schedules. Copy the schedule ID from the creation response or the list.

```bash
mn schedule list --node <owner-node>
mn schedule show <schedule-id> --node <owner-node>
```

For API clients, read `GET /api/v1/schedules/{schedule_id}?owner_node=<node>` before a change. Use its ETag in `If-Match` on PATCH or DELETE. For an ordinary schedule, PATCH `{"desired_state":"paused"}` to pause it or `{"desired_state":"running"}` to resume it. Inspect the returned status. Cancelling a schedule prevents future dispatch. Use [run controls](./monitor.mdx#control) for work already started.

## Inspect or defer a queued run

An accepted queued start appears as a `resource_wait` schedule with ID `queue_<run-id>`. Set a future ISO 8601 timestamp with an offset or `Z` to defer it.

```bash
mn schedule set-time queue_<run-id> --at <future-time> --node <owner-node>
mn schedule show queue_<run-id> --node <owner-node>
```

The run keeps its ID and becomes eligible again at that time. To cancel only the unstarted work, use `mn schedule cancel queue_<run-id> --node <owner-node>` or `mn run cancel <run-id> --queued-only`. If execution has already been admitted, the queued-only control returns a conflict.

## Overlap, missed runs, and service windows

With `prohibit_overlap` enabled, the owner checks for overlapping work. For missed occurrences, `skip` drops occurrences outside the grace period, `catchup_one` runs one missed occurrence, and `catchup_all` catches up within `catchup_limit`. If an occurrence reports `schedule_occurrence_unconfirmed`, inspect its receipt and run before trying another start.

A service occurrence starts a missing run, resumes a paused one, or records that the service is already running. A terminal service run can be replaced and its run history removed. Save any evidence you need before enabling a service schedule. The service pauses when its final active schedule window closes. Paused work can still reserve capacity.

## Event triggers

A blueprint can declare event types and payload filters for events emitted by the runtime. Use a producer supported by that blueprint. The public CLI and REST API manage schedule records. For a start from your application, use [the job run endpoint](./api.mdx#start-and-inspect-a-run).
