title: "Resources and devices"
description: "Choose capacity for a run, share a node safely, and inspect queued work."
---

Each run uses capacity on its job's owner. The owner checks current resources and reserves capacity before dispatch. Use `mn resource show` to inspect node inventory and `mn resource usage` to inspect observed usage. A read-only admission check is a snapshot. A start checks capacity again.

## Run resource budgets

In a source blueprint, set `policies.resource_allocation` in `execution.json`. The default `exclusive_node` policy reserves the whole owner. Use `shared` when compatible runs should be able to share it. Shared profiles need positive `cpu_cores` and `memory_mb`. Account for peak concurrent workers, services, and managed models, including model weights, context caches, and scratch memory.

The example below gives a CPU-only run a shared budget.

```json
{
  "policies": {
    "resource_allocation": {
      "mode": "shared",
      "cpu_cores": 2,
      "memory_mb": 4096,
      "disk_mb": 1024
    }
  }
}
```

## Device requests

A device request can select a vendor, driver, minimum memory, count, capabilities, or specific device IDs. In a shared profile, `min_memory_mb` selects hardware and `reservation_memory_mb` sets the peak budget on that device. Add the example object to the profile's `devices` array to select a CUDA GPU with at least 49,152 MiB and reserve 16,384 MiB.

```json
{
  "vendor": "nvidia",
  "driver": "cuda",
  "count": 1,
  "min_memory_mb": 49152,
  "sharing": "shared",
  "reservation_memory_mb": 16384
}
```

Use `sharing: "exclusive"` to reserve a device while sharing other node capacity. Unified-memory reservations also count against host RAM. Shared managed-model profiles support one physical GPU. Use an exclusive node profile for multi-GPU managed engines.

Docker Compose services and LLM work in the same job reuse its admitted GPU allocation. Size the budget for their combined peak use. Individual inference requests have leases so cleanup can wait for in-flight work to drain.

## Ports and volumes

Shared profiles require fixed integer ports. With automatic allocation in supported profiles, the runtime chooses a port in the configured range and exposes it as `MN_PORT_<LABEL>`. Configure the runner to publish the listener. Volume requirements select a host path on the owner. Configure the mount in the runner. Conflicting ports and overlapping writable volumes remain exclusive across shared runs.

Use allocation hints such as `MN_ALLOCATED_DEVICE_IDS` and `CUDA_VISIBLE_DEVICES` when choosing devices inside a worker. See [Docker and OpenShell](./docker_and_openshell_for_blueprints.mdx) for mounts and network boundaries.

## Admission and queueing

Manual starts default to `start_now`. A busy owner rejects the request before creating an execution. Use `--queue` with `mn job start` or `mn blueprint run` to accept a wait. Through the API, send `"admission_policy":"enqueue_if_busy"`. Scheduled starts can queue automatically.

An accepted queued run already has a run ID and an owner. It starts when compatible capacity becomes available. Use `mn run show <run-id>` to see placement and reservation state. See [Inspect or defer a queued run](./schedules-and-events.mdx#inspect-or-defer-a-queued-run).

Pausing, automatic retries, and recovery retain the claim. Terminal work can still hold capacity while the owner stops processes, drains requests, and releases model residency. Look for verified cleanup before treating the capacity as available. See [Reliability and recovery](./reliability.mdx#cancellation-and-cleanup).
