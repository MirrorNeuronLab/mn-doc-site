---
title: "Review execution and data access"
description: "Review workers, credentials, network access, and outputs before running a blueprint."
---

A blueprint can execute code, access files, pass environment variables, and call services. Use approved sample inputs while you verify its behavior.

## Review a blueprint before launch

1. Read `manifest.json`, the referenced execution and configuration documents, and the code in `payloads/`.
2. Identify the runner, mounts, uploads, `pass_env` entries, dependency setup hooks, and published ports.
3. Check model endpoints, connectors, external writes, and output destinations.
4. Validate the package with `mn blueprint validate ./my-blueprint` from its parent directory with a local runtime attached.
5. Use the package's sample mode or approved test data first. Inspect run events and results before enabling live effects.

## Choose an execution boundary

| Runner | What to review |
| --- | --- |
| HostLocal | Worker commands run with the runtime process's permissions. Use trusted code and scope accessible credentials. |
| DockerWorker or Docker Compose | Review image provenance, privileges, mounts, environment, and port publishing. |
| OpenShell | Review policy, uploads, allowed network routes, and declared output handoff. |
| Federated execution | All workers in one job run on its owner. Treat connected runtimes as one trust domain. |

Resource reservations track capacity for cooperating workloads. Use runner and host controls for filesystem, process, and network isolation. See [Prepare files and services for Docker and OpenShell](./docker_and_openshell_for_blueprints.mdx).

## Local defaults and listener checks

Run `mn runtime status` or `bin/mn-runtime status` on the installation host. Verify Core, API, Web UI, and any model gateway against the addresses you intend to expose. Core's default published host port is `55051` on loopback. The installer can bind the API beyond loopback when the Compose Web UI is enabled. The same-origin Web UI proxy can send the API credential, so restrict the Web UI listener as well.

Before enabling remote access, choose a trusted network or secure tunnel and review authentication, CORS, and firewall rules. Protect Redis and any shared storage or model gateway listeners. See [Runtime configuration](./env_variables.mdx).

## Secrets and data movement

- Keep the runtime control token, surface API bearer token, and peer credentials private. They authenticate different connections.
- Pass only the credentials each worker needs. Keep secret values out of blueprints, provider files, logs, and shared transcripts.
- Protect run artifacts, exported bundles, and job backups as you would the source data. They may include inputs, outputs, settings, or history.
- Check external model and connector destinations before sending files or prompts. Keep context-service access on the trusted runtime network.
- For external MCP access, use a job-scoped OAuth connection over trusted HTTPS. Review `get_capabilities` first. A job can expose lifecycle controls and declared domain effects in addition to bounded context and results. See [Connect a job to an MCP client](./api.mdx#connect-a-job-to-an-mcp-client).

## Respond to a suspected exposure

If you can safely stop affected work, cancel the run. Save the job ID, run ID, timestamps, and sanitized diagnostic evidence. Rotate exposed credentials and remove unintended access. Check the owning runtime for cleanup acknowledgement when a federated job shows `delete_pending`. Report security details privately to the maintainers.
